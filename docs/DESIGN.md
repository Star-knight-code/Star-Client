# Star Client design system

Everything visual in Star Client comes from one file: **`theme/tokens.json`**.
That file generates the browser prototype's CSS, the launcher's Qt stylesheet
and the C++ colour palettes, so the two surfaces cannot drift apart.

```
theme/tokens.json
        │
        ├─ tools/gen_theme.py ──► prototype/css/tokens.css        (CSS variables)
        │                    ──► src/theme/generated/*.qss        (Qt stylesheet, per theme)
        │                    ──► src/theme/generated/StarThemePalette.h  (C++ colours)
        │
        └─ (icons) ─────────────► src/theme/icons/*.svg  +  starclient.qrc
```

Run `python3 tools/gen_theme.py` after any token change. `--check` verifies
the committed output is current and is suitable for CI.

## Colour model

### Themes

| id | name | appearance | notes |
| --- | --- | --- | --- |
| `oled` | OLED Black | dark | true `#000000` base, elevated panels are near-black. The signature look. |
| `dark` | Midnight | dark | soft dark greys, less contrast, easier in a bright room |
| `light` | Daylight | light | white surfaces on a cool grey backdrop |

Each theme defines the same ~40 semantic colour names (`bg-card`, `text-muted`,
`border-subtle`, `danger`, …). Never reference a raw hex in a component — use
the semantic name, so all three themes keep working.

### Accents

Six presets — `starlight`, `aurora`, `nova`, `solar`, `emerald`, `ember` — each
defining `accent`, `accent-hover`, `accent-pressed`, `accent-soft`,
`accent-soft-strong`, `accent-ring`, a gradient pair, and `accent-rgb`.

`accent-rgb` exists because CSS needs a channel triple to build
`rgba(var(--sc-accent-rgb), 0.3)` glows that follow the accent. Qt ignores it:
the QSS resolves those to a literal at generation time.

### The star

The brand mark is a **four-pointed star**, generated by `tools/gen_logo.py`
from four circular arcs rather than hand-drawn, so every size is exact:

- tip radius `112` of a `256` viewBox
- arc bow `0.30` (0 would be a plain diamond)
- exported as `branding/svg/star-mark.svg`, `star-lockup.svg`, PNGs from
  16 px to 1024 px including @2x, and a multi-resolution `star.ico`

Colour rule: **white on dark themes, ink (`#0F131C`) on the light theme**. It is
a themed token (`star`), not a fixed colour, and never a gradient in the UI —
the gradient version is reserved for the standalone lockup asset.

## Layering

Surfaces step up in a fixed order. A component may only sit on the surface
directly above it, which is what keeps OLED black readable with no borders.

```
bg-sunken     deepest well (code blocks, logs)
bg-base       window background
bg-surface    panels
bg-card       cards
bg-elevated   popovers, menus, toasts
bg-hover      interaction states
bg-selected   selected rows, chosen cards
```

Borders are three weights only: `border-subtle` (hairlines inside a surface,
invisible on OLED by design), `border` (card edges), `border-strong`
(interactive controls). Focus is always `border-focus` plus a 2 px
`accent-ring` outline.

## Type and spacing

Font sizes run `xs 11 · sm 12 · md 13 · lg 15 · xl 19 · 2xl 24 · 3xl 32`.
Weights are `400 / 500 / 600 / 700`. Headline tracking tightens
(`-0.6px` at 3xl); labels loosen (`+0.6px` uppercase).

Spacing is a fixed 2-4-8-12-16-20-24-32-40-56 scale (`space.0` … `space.10`).
Radii are `4 · 6 · 10 · 14 · 20 · pill`. Nothing ad-hoc.

## Qt Widgets: what QSS covers, and what it cannot

This is the practical guide for porting a design to Qt Widgets. QSS is a
*subset* of CSS — it is not "CSS that happens to run in Qt".

**Supported and used here**
- background / border / border-radius / padding / margin / min-width
- `:hover`, `:pressed`, `:checked`, `:focus`, `:disabled`, `:selected`
- **attribute selectors** — `QPushButton[starRole="primary"]`. This is the
  mechanism the whole design system is built on: tag a widget with
  `setProperty("starRole", "primary")` and the stylesheet handles the rest.
- `image: url(:/resource.svg)` for indicators and arrows
- fonts, colours, and inheritance through the widget tree

**Not supported — and the workaround used**
| Missing | Workaround |
| --- | --- |
| `linear-gradient()` | a small `QWidget`/`QPushButton` subclass painting a `QLinearGradient` in `paintEvent` (see `StarButton` in the Qt harness) |
| `box-shadow` | none — elevation is expressed with borders and surface steps (already the design's approach on OLED) |
| transitions / animations | `QPropertyAnimation`, or a simple `QVariantAnimation` driver |
| `::before` / `::after` | images on the indicator with `image:` + `border-radius` clipping, as used for the toggle switch knob |
| `calc()` | generator resolves arithmetic into literals at build time |
| CSS variables | the generator resolves every token to a literal per theme |
| `text-transform: uppercase` | `QLabel` with the text already uppercased, or `QFont::setCapitalization` |

**Rendering differences to expect**
- Qt paints text with the platform font engine; the web prototype uses the
  browser's. Metrics differ by a pixel or two.
- Border-radius on a translucent widget can alias on some GPU drivers.
- `QScrollArea` does not scroll smoothly by default; the launcher adds
  kinetic scrolling itself.

None of these are blockers — the Qt harness in `prototype/qt/` reproduces the
prototype's layout, colour, typography and component styling. Gradients on the
launch button, the animated hero star and page transitions need a handful of
small C++ paint classes, which is a normal and contained cost.

## Verification

`tools/screenshot.js` renders the prototype in headless Chrome, drives the UI,
captures every screen in all three themes and fails on any console error. It is
the regression test for the design layer:

```bash
npm --prefix tools install
node tools/screenshot.js --out shots
```

The Qt harness has an equivalent mode:

```bash
QT_QPA_PLATFORM=offscreen python3 prototype/qt/starclient_qt.py --shots shots
```

Compare the two sets side by side when porting a screen — that is the fastest
way to catch a QSS rule that Qt silently dropped.
